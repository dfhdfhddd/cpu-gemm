# 阶段三：块大小参数化修改说明

## 1. 修改目的

当前文档最初记录的是 64 和 128 两种方形块大小。现在已扩展为自动测试 `Mc、Nc、Kc` 的矩形分块组合，具体实现和运行方式见《阶段三_矩形分块全组合测试说明.md》。

为了在同一次程序运行中比较 `64×64` 和 `128×128` 两种宏观分块大小，需要让分块实现能够接收不同的 `block` 值。

项目中的 `run_benchmark` 使用统一的四参数函数接口：

```text
函数(A, B, C, N)
```

因此不直接把 `block` 追加到所有 GEMM 函数的公开接口中，而是在分块文件中增加一个内部实现函数，再用两个四参数函数包装不同的块大小。

## 2. 函数关系

```text
gemm_blocked_64x64_4x4(A, B, C, N)
        └── gemm_blocked_4x4_impl(A, B, C, N, 64)

gemm_blocked_128x128_4x4(A, B, C, N)
        └── gemm_blocked_4x4_impl(A, B, C, N, 128)
```

其中：

- `gemm_blocked_4x4_impl`：真正执行两级分块和 4×4 微内核；
- `gemm_blocked_64x64_4x4`：固定使用宏观块大小 64；
- `gemm_blocked_128x128_4x4`：固定使用宏观块大小 128。

两个包装函数都只有四个参数，所以可以直接传给 `run_benchmark`。

## 3. `main.cpp` 的变化

每个矩阵规模现在依次测试：

1. `gemm_ikj`；
2. `gemm_blocked_64x64_4x4`；
3. `gemm_blocked_128x128_4x4`。

三种实现使用同一个 benchmark 流程。CSV 中会通过 `Algorithm` 字段区分两种块大小。

## 4. 正确性测试的变化

边界测试中的每个 `N` 都分别调用 64 和 128 两个版本，并与同一个独立参考结果逐元素比较。

当前覆盖的规模包括：

```text
1、3、5、100、127、128、130、256
```

这可以同时检查：

- `N` 小于块大小；
- `N` 不能被 4 整除；
- `N` 不能被 64 或 128 整除；
- 完整块和边缘块的处理。

## 5. 如何判断结果

编译并运行 benchmark 后，比较同一个 CSV 中的：

```text
gemm_blocked_64x64_4x4
gemm_blocked_128x128_4x4
```

重点观察 `N=256、512、1024` 的中位数耗时和 GFLOPS。`N=64` 或 `N=128` 时，两个块大小可能因为 `min(block, N)` 而实际使用相同或接近的范围，不适合作为主要调参依据。

## 6. 本次修改的边界

本次只完成块大小参数化和统一比较入口，没有加入 SIMD、循环展开或 OpenMP。这样可以把性能差异归因于宏观块大小，而不是多个优化同时变化。
