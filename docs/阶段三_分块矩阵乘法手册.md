# 阶段三：分块矩阵乘法手册

## 1. 阶段目标

在阶段二循环顺序实验的基础上，引入 cache blocking，也叫 tiling。核心问题是：

> 能否把一次参与计算的数据限制在较小的区域内，使 A、B、C 的工作集更容易留在缓存中，从而减少慢速内存访问？

本阶段结束时，应完成三层对比：

1. 最佳循环顺序 baseline 与基础正方形分块的对比；
2. 不同正方形 block size 的对比；
3. 正方形分块与矩形分块的对比。

最后再决定是否继续研究循环展开、指针访问和多累加器等写法优化。不要在还没有证明分块有效之前，同时加入 SIMD、OpenMP 或复杂的手工优化。

## 2. 开始前的前置条件

阶段二必须已经完成并记录：

- `gemm_ijk`、`gemm_ikj`、`gemm_kij` 都能正确计算；
- 三种循环顺序使用同一输入和同一 benchmark 规则；
- 已保存 `N=256、512、1024` 的原始 CSV；
- 已说明 row-major 下三种实现的访问路径；
- 已选出一个用于后续比较的最佳循环顺序，但不能删除其他 baseline。

如果阶段二只有代码、没有数据和解释，先补齐阶段二记录，再进入本阶段。

## 3. 本阶段的实现组织

分块实现必须独立于 `ijk/ikj/kij`，不要把分块逻辑继续塞进已有函数。

建议的文件职责：

```text
src/
  baseline/
    gemm_ijk.cpp
    gemm_ikj.cpp
    gemm_kij.cpp
  blocked/
    gemm_blocked_basic.cpp
    gemm_blocked_rectangular.cpp
    gemm_blocked_unrolled.cpp
```

其中：

- `gemm_blocked_basic.cpp`：只实现基础的 `BS x BS x BS` 正方形分块；
- `gemm_blocked_rectangular.cpp`：支持独立的 `Mc`、`Nc`、`Kc`；
- `gemm_blocked_unrolled.cpp`：在分块确认有效后，研究循环展开或多累加器；
- `calculate.cpp`：继续统一负责随机数、预热、清零、计时、统计和 CSV；
- `main.cpp`：只选择 profile 和实验配置，不复制计时逻辑。

同一个实现只改变 block size 或 `Mc/Nc/Kc` 数值时，不新建 `.cpp`，而是增加实验配置并写入 CSV。只有算法结构或写法明显改变时，才新建实现文件。

## 4. 分块算法要理解什么

矩阵乘法为：

```text
C[i][j] = sum(A[i][k] * B[k][j])
```

分块后，不再一次遍历整个矩阵，而是把三个维度切成小块：

```text
for i0 in [0, N), step block
  for j0 in [0, N), step block
    for k0 in [0, N), step block
      计算 C[i0:i1][j0:j1]
      使用 A[i0:i1][k0:k1]
      使用 B[k0:k1][j0:j1]
```

每个块的实际上界必须是：

```text
i1 = min(i0 + block, N)
j1 = min(j0 + block, N)
k1 = min(k0 + block, N)
```

这意味着 `N` 不必是 block size 的整数倍。边缘块可能比标准块小，但不能越界，也不能漏算。

## 5. 每一步要做什么

### 第 1 步：确定统一接口和参数传递方式

基础 `gemm_ijk`、`gemm_ikj`、`gemm_kij` 使用相同的四参数接口。分块实现需要 block size，因此要在实验配置中保存参数，而不是为 `16`、`32`、`64` 分别写三个函数。

建议把一次实验理解为：

```text
实现名称 + GEMM 函数 + N + block 参数 + benchmark 参数
```

例如：

```text
blocked_basic + block_size=32 + N=512 + 20 次正式计时
```

**结果要求：** 改变 block size 时只增加配置，不复制算法源文件。

### 第 2 步：实现基础正方形分块

新增 `gemm_blocked_basic`，先只支持一个统一的 `block_size`。块内计算可以采用阶段二中表现较好的循环顺序，但必须在记录中说明选择原因。

这一版暂时不加入：

- SIMD intrinsic；
- OpenMP；
- 循环展开；
- 手工预取；
- 针对某一个 `N` 的硬编码；
- 只适用于整除情况的边界假设。

**结果要求：** 对任意合理的 `N` 和 block size 都不会越界，且数学结果与 baseline 一致。

### 第 3 步：先验证边界情况

在性能测试前专门验证：

- `N=1`；
- `N=3`、`N=5` 等不能被 block size 整除的规模；
- `N=64`、`N=100`、`N=127`；
- `block_size > N`；
- `N` 恰好等于 block size；
- `N` 是 block size 的整数倍。

建议至少使用一个不能整除的规模，例如 `N=100`，因为只测 `64/128/256` 不能暴露边缘块错误。

**结果要求：** 所有规模都通过逐元素误差检查，不能只检查 checksum。

### 第 4 步：运行正方形 block size 实验

第一轮固定实现、输入、编译器和 benchmark 规则，只改变 block size。建议从以下值开始：

```text
16、32、64、128
```

正式性能规模使用：

```text
N=256、512、1024
```

开发调试可以使用 `N=64/128` 和较少迭代；最终报告必须使用统一的预热和正式次数。当前项目的正式规则是 3 次预热、20 次计时。

每组记录：

- `N`；
- 实现名；
- block size；
- 中位数、最小值、平均值、标准差；
- GFLOPS；
- checksum；
- 代码 commit；
- 测试日期和电源模式。

**结果要求：** 可以回答哪个 block size 在不同 `N` 下表现最好，以及结果是否稳定。

### 第 5 步：解释 block size 的影响

不要只挑最快的一组。分析以下现象：

- block 太小：块循环和边界控制的额外开销更明显，数据复用的收益可能抵不过管理开销；
- block 太大：工作集可能超出某级缓存，缓存淘汰增加；
- 不同 `N` 的最佳 block size 可能不同；
- 预期最快的配置不一定在每次运行都最快，应结合中位数和标准差判断；
- 编译器优化、电源模式、温度和后台负载可能影响小幅差距。

**结果要求：** 用缓存工作集和实测数据解释，而不是只写“64 最快”。

### 第 6 步：实现矩形分块

基础正方形分块确认正确后，新增 `gemm_blocked_rectangular`，分别使用：

```text
Mc：C 的行块高度，也是 A 的行块高度
Nc：C 的列块宽度，也是 B 的列块宽度
Kc：A 的列块宽度，也是 B 的行块高度
```

第一轮不要遍历过多组合，可以选择少量有代表性的配置：

```text
64 x 64 x 64
128 x 64 x 32
64 x 128 x 32
128 x 128 x 32
32 x 128 x 64
```

这里的格式是 `Mc x Nc x Kc`。每个组合都使用同一套正确性测试和 benchmark 流程。

**结果要求：** 证明矩形分块不是为了增加复杂度，而是为了分别控制 A、B、C 三个方向的工作集。

### 第 7 步：比较正方形和矩形分块

比较时必须保留：

- 相同矩阵规模；
- 相同输入；
- 相同编译器和 Release 参数；
- 相同预热和正式计时次数；
- 相同电源模式和测试日期记录方式。

至少回答：

1. 矩形分块是否在所有规模都更快？
2. 哪个维度的块大小变化最敏感？
3. 正方形分块是否只是一个方便的起点，而不是最终最优配置？
4. 某些配置变慢是因为缓存工作集、边界开销还是测试噪声？

**结果要求：** 报告同时保存所有原始配置，不只保留最快一行。

### 第 8 步：研究写法优化

在基础正方形和矩形分块都已经有数据后，再单独研究：

- 循环展开；
- 多个累加器减少依赖链；
- 指针递增代替重复下标计算；
- 更明确的局部变量和边界处理；
- 小范围内核与通用边界代码分离。

每次只改变一个主要因素。比如先测矩形分块，再测“矩形分块 + 展开 4 次”，不要一次同时改变 block 形状、循环顺序、展开和编译参数。

**结果要求：** 能区分“分块带来的收益”和“写法优化带来的收益”。

### 第 9 步：形成阶段报告

报告至少包括：

1. 分块算法和边界处理说明；
2. `ijk/ikj/kij` baseline 数据；
3. 正方形 block size 对比；
4. 矩形 `Mc/Nc/Kc` 对比；
5. 代表性写法优化对比；
6. 正确性最大误差；
7. 中位数耗时和 GFLOPS；
8. 失败配置及原因分析；
9. 最终选择的版本和下一阶段计划。

## 6. 建议的 CSV 字段

为后续 SIMD 和 OpenMP 留出字段，建议使用：

```text
implementation,N,dtype,threads,block_size,Mc,Nc,Kc,unroll,
median_ms,min_ms,mean_ms,stddev_ms,gflops,checksum
```

非分块实现的 `block_size/Mc/Nc/Kc` 可以写 `0`，单线程写 `threads=1`，未使用循环展开时写 `unroll=1`。字段含义必须在报告或 README 中说明。

## 7. 运行 profile

继续使用阶段二准备的运行范围：

| profile | 用途 | 本阶段典型内容 |
|---|---|---|
| `smoke` | 快速检查 | 当前分块实现，`N=64/100/128`，少量重复 |
| `tune` | 调 block 参数 | 只跑 `blocked_basic` 或 `blocked_rectangular` 的多组参数 |
| `compare` | 正式比较 | 最佳 baseline、最佳正方形分块、代表性矩形分块 |
| `full` | 阶段验收 | 所有保留实现、所有正式规模、完整统计 |

调参时不要每次运行所有历史版本；但正式报告和阶段验收必须保留基线对照。

## 8. 常见错误

- 只测试能被 block size 整除的 `N`，导致边缘块代码从未验证；
- 在计时区间内分配矩阵、生成随机数、清空整个矩阵或写 CSV；
- 为每个 block size 复制一份几乎相同的 `.cpp`；
- 正方形分块和矩形分块使用了不同输入或不同编译参数；
- 把循环展开、AVX2、OpenMP 一次加入，无法判断收益来源；
- 只保存最快配置，删除慢配置和失败配置；
- 用 checksum 代替逐元素正确性验证；
- 误以为 block size 越大越快，忽略缓存容量和工作集；
- 为某一个矩阵规模硬编码，导致其他规模错误或失去通用性。

## 9. 阶段三验收标准

- [ ] 基础正方形分块独立成新的实现文件；
- [ ] 能处理 `N` 不能整除 block size 的边界情况；
- [ ] `N=1、3、5、64、100、127` 等边界和非整除规模通过正确性测试；
- [ ] `block_size=16、32、64、128` 有统一条件下的性能数据；
- [ ] 每个结果包含中位数、最小值、平均值、标准差、GFLOPS 和 checksum；
- [ ] 实现了矩形分块并测试多组 `Mc/Nc/Kc`；
- [ ] 正方形和矩形分块使用相同输入、编译参数和 benchmark 规则；
- [ ] 保留慢配置和失败配置，并记录原因；
- [ ] 能解释 block size 和缓存工作集的关系；
- [ ] 写法优化每次只改变一个主要因素；
- [ ] 阶段报告、原始 CSV 和 Git commit 已保存。

完成本阶段后，才进入 SIMD/AVX2 或 OpenMP。下一阶段的优化必须以本阶段选出的最佳分块版本为输入，同时继续保留 `ijk/ikj/kij` 作为参照。
