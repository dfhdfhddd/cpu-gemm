# 阶段二：循环顺序与缓存手册

## 1. 阶段目标

在不改变 GEMM 数学结果、接口、输入和 benchmark 规则的前提下，比较 `ijk`、`ikj`、`kij` 三种循环顺序，建立“访问模式 -> 缓存行为 -> 性能结果”的解释链。

最终不是只得出“某个版本更快”，而是能具体说明 A、B、C 在 row-major 布局下各自是连续访问还是跨行访问，以及这种访问如何影响缓存行利用率。

## 2. 开始前的前置条件

阶段一必须已经冻结：

- `gemm_ijk` 的代码和行为不再修改；
- 正确性测试通过；
- Release benchmark 可重复运行；
- 最终 CSV、硬件和编译环境已有记录。

如果 baseline 仍在变化，先回到[阶段一手册](阶段一_基线闭环手册.md)，不要开始阶段二。

## 3. 开始前必须准备的实验框架

阶段二开始时就应把“实现代码”和“实验控制”分开。后续会出现 `ijk`、`ikj`、`kij`、正方形分块、矩形分块、循环展开版、SIMD 版和多线程版。如果每增加一种实现就复制一份 `main.cpp` 或 benchmark，文件会越来越臃肿，计时规则也容易不一致。

### 3.1 按优化家族拆分源文件

每种有独立算法结构的实现使用独立的 `.cpp` 文件。建议的目录方向如下：

```text
src/
  baseline/
    gemm_ijk.cpp
    gemm_ikj.cpp
    gemm_kij.cpp
  blocked/
    gemm_blocked_basic.cpp
    gemm_blocked_rectangular.cpp
    gemm_blocked_unrolled.cpp
  simd/
    gemm_avx2.cpp
  parallel/
    gemm_openmp.cpp
```

阶段二实际只需要新增 `gemm_ikj.cpp` 和 `gemm_kij.cpp`。后面的文件是规划，不要求现在创建空文件。

文件职责要固定：

- `gemm_ijk.cpp`、`gemm_ikj.cpp`、`gemm_kij.cpp`：只实现对应循环顺序；
- `gemm_blocked_basic.cpp`：最简单的正方形分块；
- `gemm_blocked_rectangular.cpp`：支持 `Mc/Nc/Kc` 三个独立的矩形分块参数；
- `gemm_blocked_unrolled.cpp`：在分块基础上研究循环展开、指针访问或累加器写法；
- `calculate.cpp`：统一生成输入、预热、清零、计时、统计和 CSV；
- `main.cpp`：选择本次运行的实验配置，不放具体 GEMM 循环和计时细节。

同一算法只改变 block size、线程数或矩阵规模时，不需要复制新的 `.cpp`。这些应作为实验参数记录在 CSV 中。只有循环结构、访问方式、指令集或并行模型发生变化时，才建立新的实现文件。

### 3.2 统一实现接口

所有可以直接比较的基础实现都遵守阶段一的函数约定：输入 `A`、`B`、`C` 和 `N`，函数只计算 `C`。调用者负责内存和初始化，函数内部不得生成随机数、计时、写 CSV 或打印日志。

分块实现需要额外参数时，不要为每个 block size 写一个函数。应让同一个分块函数接收参数结构，例如记录 `Mc`、`Nc`、`Kc`；具体字段名称以后按代码实现确定。

这样可以区分两类变化：

| 变化 | 是否新建 `.cpp` | 记录方式 |
|---|---|---|
| `blocked_rect` 的 `Mc/Nc/Kc` 数值变化 | 否 | 同一实现名，CSV 多行参数记录 |
| 正方形分块改为支持独立 `Mc/Nc/Kc` | 是 | 新实现名，例如 `blocked_rect` |
| 在分块内加入循环展开或多累加器 | 建议是 | 新实现名，例如 `blocked_unrolled` |
| 加入 AVX2 或 OpenMP | 是 | 新阶段、新实现和新实验记录 |

### 3.3 建立实现注册表

不要在 `main.cpp` 中写一长串硬编码调用，也不要因为注册了所有实现就每次全部运行。准备一个“实验配置列表”，每条配置至少包含：

- 实现名称，例如 `ijk`、`ikj`、`blocked_rect`；
- 对应的 GEMM 函数；
- 可选参数，例如 `Mc`、`Nc`、`Kc`、线程数或展开因子；
- 是否纳入当前 profile；
- 输出时使用的参数标签。

主程序只负责从这个列表中选出本次要运行的配置，再交给统一 benchmark 流程。概念关系如下：

```text
main.cpp
  -> 选择实验 profile
  -> 取得实现配置列表
  -> calculate.cpp 统一执行
       -> 生成同一份输入
       -> 预热、计时、统计
       -> 写入 CSV
```

### 3.4 预先定义运行 profile

建议至少准备以下四种运行范围：

| profile | 用途 | 运行内容 |
|---|---|---|
| `smoke` | 开发后快速确认 | baseline 加当前正在修改的实现，`N=64/128`，少量重复 |
| `tune` | 调参数 | 只运行一个实现，例如 `blocked_rect`，遍历多组 `Mc/Nc/Kc` |
| `compare` | 阶段对比 | `ijk`、`ikj`、`kij`，统一 `N=256/512/1024` 和正式重复次数 |
| `full` | 阶段或发布前验收 | 运行所有保留实现、全部最终规模和完整统计 |

开发期间主要用 `smoke`，调矩形分块时用 `tune`，写阶段报告时用 `compare`，最终提交前才用 `full`。这样不会因为新增了十几个实验配置，就每次都等待全部版本跑完。

如果暂时没有命令行 profile，至少在配置列表中明确当前启用项，并在实验记录中写明本次实际运行了哪些实现。不要靠注释掉半个 `main.cpp` 来切换实验。

### 3.5 设计统一结果字段

为了让后续正方形分块、矩形分块和多线程结果能放在同一个 CSV 中，结果字段应能描述实现和参数。建议至少包括：

```text
implementation,N,dtype,threads,Mc,Nc,Kc,unroll,
median_ms,min_ms,mean_ms,stddev_ms,gflops,checksum
```

不适用的参数使用固定值或空值，例如非分块实现的 `Mc/Nc/Kc=0`，单线程使用 `threads=1`。不要只把参数写在终端标题里，否则后面无法知道某一行数据对应什么配置。

### 3.6 为优化过程保留证据

优化过程需要保留，但不应该靠复制大量源文件体现。每一个可比较的实现或重要实验至少保留：

1. 一个清晰的实现文件或参数配置；
2. 一次 Git commit，说明改动目的；
3. 一组原始 CSV 数据；
4. 一段实验记录，说明为什么保留、淘汰或继续调参。

失败的矩形分块参数也可以保留在调参 CSV 中。最终报告可以只展示代表性配置，但不要删除原始数据后再声称“试过”。

## 4. 每一步要做什么

### 第 1 步：写出三种访问顺序

保留原始 `ijk`，新增只改变循环顺序的 `ikj` 和 `kij`。三种实现必须使用相同接口、相同 `float` 类型和相同 row-major 布局。

概念形式：

```text
ijk: for i -> for j -> for k
ikj: for i -> for k -> for j
kij: for k -> for i -> for j
```

不要在这一步加入分块、SIMD、OpenMP、转置或额外编译参数。

**结果要求：** 三个实现只有循环顺序不同，能够被同一个 benchmark 函数调用。

### 第 2 步：先做正确性回归

对三种实现运行阶段一的全部确定性和随机测试，比较输出误差、失败位置和 checksum。不能因为“只是换循环”就跳过正确性测试。

**结果要求：** 三种实现都通过同一套测试，误差在相同阈值内。

### 第 3 步：固定公平测试条件

使用同一编译器、同一 Release 参数、同一随机种子、同一输入生成流程、同一预热次数和正式次数。第一轮建议测试 `N=256、512、1024`，保留阶段一的 `64` 和 `128` 作为快速回归规模。

**结果要求：** 除循环顺序外，其他变量不变；每个实现都生成结构一致的 CSV 记录。

### 第 4 步：画出访问路径

在实验记录中分别写清楚：

- `ijk` 中 `A[i*N+k]` 连续，`B[k*N+j]` 按列方向跳跃，`C[i*N+j]` 在内层循环中反复写同一个元素；
- `ikj` 中固定 `i,k` 后，`j` 连续访问 `B[k*N+j]` 和 `C[i*N+j]`，更适合 row-major 连续访问；
- `kij` 中固定 `k,i` 后，`j` 同样连续访问 B 和 C，但 A 的读取方式和累加顺序不同。

**结果要求：** 不只记录快慢，还能对每种顺序指出至少一个连续访问和一个不连续访问。

### 第 5 步：运行 benchmark

每个规模先预热，再正式运行 20 次，记录中位数、最小值、平均值、标准差、GFLOPS 和 checksum。运行顺序可以交错，例如 `ijk -> ikj -> kij -> ijk ...`，避免某一个实现总是在温度或频率变化的固定阶段运行。

**结果要求：** 每种实现、每个规模都有完整 CSV 记录，并且 checksum 与 baseline 一致或在浮点误差范围内一致。

### 第 6 步：分析缓存与性能

将实测数据与访问路径对应起来，回答：

1. 哪种顺序在当前 CPU 和规模下最快？
2. 它是否让内层循环更多地访问连续内存？
3. `N` 增大后，差距是否扩大或缩小？
4. 是否出现标准差变大、频率下降或缓存容量影响？
5. 如果结果与预期相反，是否可能是编译器优化、温度、电源模式或测试噪声造成的？

**结果要求：** 结论同时包含数据和机制解释，不能只写“ikj 更快”。

### 第 7 步：形成阶段报告

保存原始 CSV，制作至少一张“矩阵规模-中位数耗时”或“矩阵规模-GFLOPS”表/图，并记录代码 commit、环境、测试日期和结论。

**结果要求：** 别人只看阶段报告和 CSV，就能复现实验并理解你的结论。

## 5. 常见问题

- 把三种实现写在同一个函数里，导致循环边界或初始化不一致；
- 只测一次，或者三种实现使用了不同的输入；
- 计时包含随机数生成、内存分配、正确性检查或 CSV 写入；
- 为了让某个版本更快而单独改变编译参数；
- 看到结果反常就修改 baseline，而不是先检查温度、电源模式和测试顺序；
- 忽略浮点累加顺序变化，要求三个版本逐元素完全相等。

## 6. 阶段二验收标准

- [ ] `ijk`、`ikj`、`kij` 三种实现都能编译；
- [ ] 三种实现通过同一套正确性测试；
- [ ] 只改变循环顺序，没有混入分块、SIMD 或多线程；
- [ ] 使用统一输入、编译参数、预热和正式次数；
- [ ] `N=256、512、1024` 都有完整原始 CSV；
- [ ] 每种实现都有中位数、最小值、平均值、标准差、GFLOPS 和 checksum；
- [ ] 能解释三种顺序的 row-major 访问路径；
- [ ] 能用数据解释性能差异和异常结果；
- [ ] 阶段报告和代码 commit 已保存。

完成全部验收项后，才进入阶段三的分块矩阵乘法。
