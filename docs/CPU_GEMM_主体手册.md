# CPU GEMM 主体手册

> 这是项目的总导航。每个阶段的具体操作、命令、检查项和验收标准放在对应的阶段手册中。
> 当前项目的第一阶段已完成主要闭环，第二阶段尚未开始。

## 1. 项目目标

本项目通过逐步实现和比较不同版本的 CPU 矩阵乘法（GEMM），理解：

- 矩阵乘法的数学结构和 `N x N` row-major 数据布局；
- 循环顺序对缓存局部性的影响；
- 分块、SIMD 和多线程如何提高吞吐量；
- 如何设计可复现、可信的性能测试；
- 为什么成熟数学库通常比直接实现更快。

最终要达到的结果不是只得到一个“最快”的数字，而是做到：**实现正确、测试可复现、数据可比较、原因能解释**。

## 2. 重点等级

- **核心**：必须自己理解，能解释原因并定位问题。
- **理解**：知道用途、输入输出和常见问题，需要时会查文档。
- **复用**：可以复制模板，但必须会运行、会检查结果、会看报错。
- **以后**：当前只了解名称，不提前实现，等前置阶段验收后再做。

“复用”不等于完全不管。至少要明确它的输入、输出、运行方式，以及它是否进入计时区间。

## 3. 项目约定

- 矩阵为方阵：`C = A x B`，尺寸为 `N x N`。
- 数据使用连续的 row-major 数组，基线使用 `float`。
- `gemm_*` 函数只负责计算，不负责分配、随机数、计时或打印。
- 正确性测试和性能测试分开；正确性检查不能放进计时区间。
- 所有实现使用相同的输入、矩阵规模、编译器和 benchmark 规则。
- 性能只使用 Release 构建；报告同时保留原始 CSV 和解释性结论。

## 5. 通用 benchmark 规则

每次比较必须固定：矩阵规模、数据类型、输入数据、编译器、编译参数、线程数、预热次数、正式次数、电源模式和测试日期。

推荐流程：

1. 先运行正确性测试；
2. 预热 2～3 次；
3. 正式运行至少 10 次，当前基线使用 20 次；
4. 每次正式运行前重置 `C`；
5. 记录中位数、最小值、平均值、标准差和 GFLOPS；
6. 保存 CSV，不只保留终端截图；
7. 只有同一条件下的数据才能直接比较。

对于 `N x N` GEMM：

```text
GFLOPS = 2 x N^3 / seconds / 1e9
```

中位数是主要比较指标，平均值、最小值和标准差用于判断稳定性和辅助解释。

## 8. 总体完成标准

项目最终完成时应具备：

- 至少五种可区分的 GEMM 实现；
- 自动正确性测试；
- 可复现的 Release 构建命令；
- 至少三种矩阵规模；
- 中位数、GFLOPS 和原始 CSV；
- 循环顺序、分块、SIMD、多线程和成熟库的对比；
- 每次优化都有“改了什么、为什么可能更快、结果是否符合预期”的解释；
- README 能让其他人完成构建、测试和 benchmark。
